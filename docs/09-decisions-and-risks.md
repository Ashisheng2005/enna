### Q2 QQ 账号与群聊策略

**问题**：用哪个 QQ 号？进不进群？群聊是否允许 L0？

| 选项 | 说明 |
|---|---|
| A（建议） | 专用小号，**只私聊**，不进任何群。攻击面最小，风控概率最低 |
| B | 专用小号 + 进 1–2 个内部运维群，群内仅 L0 且仅响应 @ |
| C | 使用现用账号 —— **不建议**：封号损失大，且个人社交关系会污染权限模型 |

**影响**：M1 的群聊相关工作量（渲染、脱敏、限流）取决于此。**建议**：先 A，M3 之后再评估 B。

**同时需要决定的**：机器人账号是否允许出现"它在上线/离线"的可见状态；是否允许主动加好友（建议一律禁止）。

### Q3 设备规模与网络可达性

> ⚠️ **架构分叉点**

**问题**：控制机能否直连所有受管设备的 22 端口？

| 场景 | 影响 |
|---|---|
| 全部内网可达（≤ 50 台） | **中心化 SSH 方案直接可用**（本设计默认）。实现最简单 |
| 部分设备在 NAT 后 / 跨地域 / 无固定 IP | 需要 **edge agent 模式**（设备侧安装 agent 主动拨出，零入站端口）。这是一次**架构级增补**，不是小功能 |
| 规模 > 200 台 | 需要分区控制机 + 设备状态缓存；审计量级也要重新评估 |

**本设计的处理**：`internal/sshx` 被设计为**可替换的传输层**接口，`Target` 抽象不假设传输方式 —— 这样将来加 edge agent 时，技能层与策略层零改动。但**我需要在设计早期就知道是否需要它**，因为 edge agent 会引入：设备侧二进制分发、升级、设备侧策略缓存（离线时怎么办）、双向信任。

**建议**：先明确回答"最大的那台/最难连的那台设备，控制机能直接 SSH 吗"。如果是"不能"，请在 M0 之前告诉我，我会把传输层抽象提前做实。

### Q5 模型供应商与数据合规

> ⚠️ **硬约束**

**问题**：设备日志、进程列表、配置内容可能含用户数据与内部信息。这些内容会进入 LLM 上下文。

必须明确：

1. 是否允许发送到**境外** provider？
2. 是否允许发送到**境内公有云** provider？
3. 是否需要**本地/私有部署**模型（如自建推理）？
4. 是否有行业/等保合规要求（日志留存、数据不出境）？

**本设计的处理**：路由键第 1 条就是数据合规约束（[`06` §5.2](06-brain-orchestration.md#52-路由键按优先级)）。策略是"**先定合规边界，再选模型**"，而不是"先选模型，再想办法合规"。

**建议**：
- 若数据敏感 → 敏感档位强制境内 provider 或私有部署；`classify`/`write` 档位可用便宜模型（不接触原始设备数据）。
- 无论选什么，**默认开启脱敏**，并让"是否发送原始日志"成为一个可配置的显式决策，而不是隐含默认。

### Q6 是否采用 MCP 作为工具协议

**问题**：是用自有 gRPC 技能注册表（本设计），还是用 MCP 以便复用生态（如各类 ops MCP server）？

| 选项 | 说明 |
|---|---|
| A（建议） | **内核用自有 gRPC 注册表**（强类型、可强约束 schema/风险/审计），MCP 仅作**受控外接**：只读类 MCP server 可直接接入；写操作类必须经我们的 policy 包装后才暴露给模型 |
| B | 全面改用 MCP | 生态复用度高，但 MCP 的工具描述是**纯文本、由 server 自述**，风险等级与参数约束无法被我们的内核强制校验，等于把安全模型建立在外部 server 的自觉上 |
| C | 完全不碰 MCP | 最安全，但放弃生态 |

**建议**：A。理由：MCP 的价值在"接入别人的只读数据源"，而我们的核心诉求是"**对写操作有强约束**" —— 这两件事的性质不同，应该用不同机制。

### Q7 入站附件（图片/文件）如何处理

**问题**：用户发一张截图说"照这个改配置"，系统要不要处理？

| 选项 | 说明 |
|---|---|
| A（建议，初期） | 不处理附件，只记录元数据并回复"暂不支持图片输入" |
| B | 支持图片 → OCR/视觉模型解析 → 作为**不可信数据**进入上下文，需二次确认操作内容 |
| C | 支持文件上传 → 存 artifacts → 由技能读取 |

**风险**：图片/文件名是新的注入载体（[`02` T3](02-security-model.md#2-威胁模型)）。**建议**：初期 A，M5 之后再评估 B/C，且必须纳入对抗用例集。

### Q8 部署环境事实

需要确认：

1. 控制机的操作系统与版本（影响 systemd 单元、包管理、依赖）。
2. 控制机是否能稳定访问模型 API（网络策略/代理）。
3. NapCat 计划部署在哪台机器上，出口 IP 是否固定。
4. 受管设备的发行版分布（Debian 系 / RHEL 系）—— 直接影响技能里 `journalctl`、`ss`、`ip`、`apt`/`dnf` 的可用性。
5. 受管设备是否允许创建 `enna-ops` 账号与配置 `sudoers`（[`02` §3.4](02-security-model.md#34-设备侧最小权限)）。
6. 是否存在**跳板机**要求。

**影响**：技能实现细节与 M0 验收方式。**建议**：先选 1–2 台"标准"设备作为 M0 的靶机，把发行版差异留到 M3。

### Q13 网络设备何时纳入

你的原始设想里有"网络管理员"成分（SNMP、拓扑、接口指标）。

**本设计的处理**：首批只做 Linux/SSH（你已确认），但技能注册表与设备模型已预留 `TargetKind` 以便扩展。接入网络设备时新增的是：

- 新传输层（SNMP / RouterOS API）——与本次的 `sshx` 并列。
- 新的技能族（`netdev.interface.*`、`netdev.route.*`、`netdev.vlan.*`）。
- 拓扑发现（从主机邻居表推导）与主机↔网络设备链路映射。

**建议**：M5 之后单独评估。不要在 SSH 内核还没稳的时候并行做两套传输。

## 第二部分 · 已做出的关键取舍（Decision Log）

记录下来，是因为**代价比决定本身更重要** —— 将来想推翻某个决定时，应该先看它的代价是否可接受。

| # | 决定 | 理由 | **代价（明确接受）** |
|---|---|---|---|
| D1 | 模型不生成命令，只选技能 + 参数 | 消除"提示注入→RCE"的直连路径 | 灵活性下降。新运维需求必须先写技能代码，无法"临场让模型想办法" |
| D2 | 变更是"计划级审批"而非"命令级审批" | 避免审批疲劳；让确认有意义 | **变更执行后无法"看结果再决定下一步"**。多步链式变更必须拆成多次任务 |
| D3 | 入站用异步 `Submit` + 出站 `Push`，不用请求-响应流 | 任务生命周期与连接解耦，长任务不丢结果 | brain 必须自己管会话状态；实现比同步流复杂 |
| D4 | 群聊硬限 L0，且不可配置上调 | 群成员不可信；防社会工程 | 群里不能执行任何写操作，必须切私聊。牺牲便利换安全 |
| D5 | 安全提示词是代码常量，角色卡不可覆盖 | 让安全条款不可被配置/注入修改 | 调整安全行为必须改代码并发版，不能改配置文件 |
| D6 | 审计不可用时拒绝 L1 以上操作（fail-closed） | 不可审计 = 不可执行 | 审计盘满/权限错会导致**写操作全面不可用**。这是刻意的 |
| D7 | 首次连接设备不做 TOFU，需人工确认指纹 | 防中间人 | 新增设备多一步人工操作 |
| D8 | 不提供 `shell.run` 任意命令透传 | 保住 D1 的安全性论证 | 遇到没写技能的场景会"卡住"，需要临时用 CLI 或补技能 |
| D9 | 不提供"临时连接任意主机" | 防模型诱导接入攻击者控制的机器 | 排障新机器时须先 `enna device add` |
| D10 | `tmp.prune` 定 L2（非 L3） | 爆炸半径有界（限路径/时长/只删普通文件/不跟符号链接/先干跑列清单） | 需要精细的实现约束来"配得上"这个等级；约束一旦放松就必须升级为 L3 |
| D11 | 只用 Go 写内核，Python 只做推理 | 安全边界不进 LLM 层 | 两套语言、两套构建、两套依赖管理；跨语言调试成本 |
| D12 | 不引入 Docker（当前环境无） | 与现状一致，减少依赖 | 测试环境搭建需另想办法（如本地 sshd + 测试用户替代容器靶机） |
